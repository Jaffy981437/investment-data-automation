## 一、關鍵:不要用社群那套「截圖點像素」

社群的做法是讓 AI 截圖看畫面、算出按鈕在哪、點下去。這條路能動,但很脆弱:
介面一改版、模擬器解析度一變、彈窗擋住,座標就全錯。

**Android 模擬器支援 ADB,可以直接拿到畫面的 UI 元素樹。**

```bash
adb shell uiautomator dump /sdcard/ui.xml
adb pull /sdcard/ui.xml
```

拿到的 XML 裡每個元件都有 `text`、`resource-id`、`bounds`(精確座標)。
於是「點選底部的自選」不再是「點 (540, 1850) 這個像素」,而是:

> 找到 `text="自選"` 的節點 → 讀它的 bounds → 點那個中心點

**介面位置改了,程式照樣找得到。**這是這兩種做法的根本差別。

| | 截圖點像素(社群) | ADB + UI 樹(建議) |
|---|---|---|
| 定位方式 | 猜像素座標 | 用元件文字 / id |
| 介面改版 | 直接失效 | 多半仍可運作 |
| 輸入文字 | 模擬鍵盤逐字敲 | `adb shell input text` |
| 驗證結果 | 再截圖用眼睛看 | 重新 dump,直接比對文字 |
| 需要 AI 視覺判讀 | 每一步都要 | 只在拿不到節點時 |
| 可版控 / 可重跑 | 難 | 就是一般程式 |

另一個好處:ADB 走命令列,不需要 Computer Use 的桌面控制權限,
也不會因為你剛好在用電腦、滑鼠移到模擬器上而出錯。

## 二、兩條硬體路線,先選一條

### 路線 A:MuMuPlayer 模擬器(社群走的)

- ✅ 常駐電腦,不佔手機,可排程
- ✅ 解析度可固定,自動化最穩
- ❌ 要另外裝模擬器、在模擬器內登入 Google 帳號與方舟帳號
- ❌ 吃記憶體(社群建議記憶體多一點)

### 路線 B:你的實體 Android 手機 + USB 傳輸線

- ✅ **完全不用裝模擬器**,方舟 APP 你手機上本來就有、也已經登入
- ✅ 同一套 ADB 程式碼,兩條路線通用
- ❌ 要開發人員選項 + USB 偵錯
- ❌ 執行時手機要接著電腦

> **待確認:你的手機是 Android 還是 iPhone?**
> 是 Android → 路線 B 可以省掉整個模擬器安裝,建議優先。
> 是 iPhone → 只能走路線 A(iOS 沒有 ADB 這種等價機制,自動化門檻高很多)。

### 建議設定(會直接影響自動化穩定度)

- **固定解析度**,例如 1080×1920 / DPI 320,設定後就別再改
- 關閉模擬器的自動更新與開機動畫
- 電腦電源設定改成「不休眠」(社群踩過這個坑)

### 我要做的

- 確認 adb 可連線、確認方舟的 package name
- 寫 dump / 定位 / 點擊 / 驗證的程式
- 寫差異報告與寫入流程

### 連線指令

MuMuPlayer 12 的 ADB 埠是 `127.0.0.1:16384`(第一個實例,每多一個實例 +32)。
adb 可用 MuMuPlayer 內建的(安裝目錄 `shell\adb.exe`),或另裝 Android Platform Tools。

```bash
adb connect 127.0.0.1:16384
adb devices
adb shell pm list packages | findstr -i ark
```

實體手機則是接上 USB、開啟 USB 偵錯後直接 `adb devices`。

## 四、第一件事:可行性驗證(在寫任何自動化之前)

**這步沒過,後面整套規劃都要改。**

方舟運算若是用 Flutter / React Native 這類框架寫的,`uiautomator dump` 可能
只會看到一整塊 View,拿不到「自選」「策略」這些文字節點。這無法從外部推測,
只能實測。

### 驗證腳本會做的事

1. `adb connect` 並確認裝置在線
2. 開啟方舟運算
3. `uiautomator dump` 抓 UI 樹
4. 統計:總節點數、有 `text` 的節點數、有 `resource-id` 的節點數
5. 檢查是否找得到「自選」「策略」「運算」這幾個關鍵字

### 三種結果與對應

| 結果 | 判讀 | 對應方案 |
|---|---|---|
| 找得到文字節點 | 原生 Android 元件 | ✅ 走 ADB 路線,可靠 |
| 節點很少、沒有文字 | Flutter / RN / 遊戲引擎 | ⚠️ 混合:ADB 截圖 + 視覺定位,座標仍用 adb 點 |
| 完全 dump 不出來 | 有反自動化保護 | ❌ 退回 Computer Use 截圖點擊(社群那套) |

即使落到最壞情況,ADB 仍比較好用 —— `adb exec-out screencap -p` 截圖比抓桌面視窗乾淨,
點擊也不受滑鼠位置影響。

## 五、程式架構

```
scripts/ark/
├─ adb_client.py       # 封裝 adb:connect / dump / tap / text / screencap
├─ ark_ui.py           # 方舟畫面的元素定位與頁面切換
├─ probe_ark.py        # 第四節的可行性驗證腳本
├─ diff_holdings.py    # 比對 csv 與方舟現況 → 差異報告
└─ sync_to_ark.py      # 主流程(預設 dry-run)
```

### 主流程設計

```
1. 讀 data/holdings/holdings_latest.csv
2. 開啟方舟 → 自選 → 調節庫存 → 編輯我的庫存股
3. dump UI,讀出方舟目前的庫存(代號 / 股數 / 均價)
4. 比對,產生差異報告:
      要更新的、數值相同可略過的、要新增的、方舟有但券商沒有的
5. ⏸ 停下來,把報告給你看          ← 預設停在這
6. 你確認後才逐檔寫入
7. 每寫一檔就重新 dump 驗證,不一致立即停止
```

## 六、安全機制(這段最重要)

社群的指令裡有「**每日清空並重建布局自選**」這種刪除動作,而且他們自己就
發生過「更新到另一個帳號的庫存」。所以:

1. **預設 dry-run。**先出差異報告,人工確認後才寫入。
2. **不自動執行清空類動作。**清空布局自選這步需要你當下明確同意,不排進自動流程。
3. **只改有差異的欄位。**數值相同的不重複寫入(這也是社群指令的要求)。
4. **絕不自動刪除庫存。**券商沒有但方舟有的股票,只回報,不動手。
5. **不碰排序。**不拖曳右側漢堡圖示。
6. **每步驗證。**寫入後 dump 比對,不一致就停,不繼續往下做。
7. **帳號確認。**開始前先確認登入的是哪個帳號,和預期不符就停。
8. **不下單。**這整套只做庫存資料同步,不碰任何交易功能。

### 精度規則(照方舟要求)

- 股數:保留完整小數位,不四捨五入(54.17777 就輸入 54.17777)
- 均價:四捨五入到小數點後 2 位(584.936220 → 584.94)
- 代號:純英文大寫(美股)或數字(台股);若跳出中文輸入法要先清掉

## 七、已知風險

| 風險 | 影響 | 因應 |
|---|---|---|
| APP 改版,元件文字或結構變動 | 自動化失效 | 用文字定位比像素耐改版;失敗即停不亂點 |
| uiautomator 拿不到節點 | 要退回視覺路線 | 第四節先驗證再投入 |
| 輸入法跳中文候選字 | 代號輸入錯誤 | 切英文輸入法;寫入後 dump 驗證 |
| 數字輸入遺失第一碼 | 股數錯誤 | 逐欄清空再輸入,寫入後驗證 |
| 模擬器當掉 / 電腦休眠 | 流程中斷 | 關閉休眠;流程可重跑且具冪等性 |
| 誤觸到下單功能 | **實際交易** | 流程只走庫存編輯頁;遇到非預期畫面立即停止 |
